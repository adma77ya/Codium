Codium: a coding-contest platform, explained from the first decision to the last

Every explanation below has the real code next to it. Read the "Say it like this" boxes aloud. Read the "Be honest here" boxes before an interviewer finds the gap for you.

The 60-second pitch

Codium is a distributed coding-contest platform. A user writes code in the browser and submits it. A Go API saves the submission in Postgres, puts its id on a Redis queue, and replies 202 straight away. A separate worker pops the id and runs the code in a locked-down Docker container with no network and hard CPU, memory and process limits. It writes the verdict to Postgres, updates a Redis sorted set for the leaderboard, and publishes the change. The API's WebSocket hub is subscribed to that channel and pushes the update to every open browser. It runs on AWS: EC2 for nginx, the API, the worker and Docker; RDS Postgres and ElastiCache Redis in private subnets that only the EC2 security group can reach.

Three ideas to name early:

  1. Postgres is the source of truth. Redis holds only derived or transient state: the queue and the ranking. Anything in Redis can be rebuilt.
  2. Slow work is asynchronous. The API records and enqueues. Judging time never blocks a request.
  3. The API and the worker share nothing but Postgres and Redis. That is why each one scales on its own.

Part A. How it works, in plain words

This part is for reading and understanding, not for answering questions. Follow one submission from the moment you press Submit. Each step says what happens, which file does it, and shows the one snippet that matters.

flowchart TB
  A[1 You press Submit] --> B[2 API checks your login token]
  B --> C[3 API saves the submission as pending in Postgres]
  C --> D[4 API puts the id on a Redis queue]
  D --> E[5 API answers 202 right away]
  D --> F[6 Worker takes the id off the queue]
  F --> G[7 Worker claims it so nobody else judges it]
  G --> H[8 Worker runs your code in a locked Docker box]
  H --> I[9 Worker saves the verdict]
  I --> J[10 Worker updates the leaderboard in Redis and announces it]
  J --> K[11 API pushes the change to every open browser]

Steps 1 to 5 take milliseconds. Steps 6 to 11 happen in the background while your browser waits.

Step 1. The browser sends the code

The React page calls POST /api/submit with your token in the Authorization header. The code lives in web/src/api/judge.ts.

Step 2. The API checks who you are

A small wrapper (middleware) runs before the handler. It reads the token, verifies the signature and expiry, and stores your user id for the handler to use. A bad or missing token ends here with 401.

Steps 3 to 5. Save first, queue second, answer immediately

The API never judges anything. It writes the submission to Postgres with status pending, pushes only the id onto a Redis list, and replies 202 Accepted. Saving first means the submission cannot be lost even if Redis is down.

Step 6. The worker waits on the queue

The worker is a separate program. It sits in BRPOP, which blocks inside Redis until an id arrives. No polling loop. It runs several of these loops side by side (goroutines), so several submissions are judged at once.

Step 7. The worker claims the job

One SQL statement flips pending to running, but only if the row is still pending. Postgres runs it atomically, so if two workers ever got the same id, only one would win.

Step 8. Your code runs in a locked box

For each test case the worker starts a fresh Docker container that cannot use the network, has a CPU, memory and process limit, a read-only filesystem and a non-root user. Your code reads the test input from stdin. The worker compares what it prints with the expected output.

The outcome decides the verdict: compile failed, timed out, crashed, wrong output, or all tests passed.

Step 9. The verdict is saved

Step 10. The leaderboard is recalculated

The worker recounts that one user's solved problems and penalty from Postgres, turns them into a single score, writes it into a Redis sorted set, and publishes a message on a Redis channel.

Step 11. Browsers are told

The API has one subscription to that Redis channel. When a message arrives, the WebSocket hub copies it to every connected browser. The browser treats it as "something changed" and asks the API for the fresh leaderboard.

Security groups are firewalls attached to a resource. The database rules name the EC2 security group as the allowed source, so only that server can connect.

C1. Create the server (EC2)

  1. In the AWS console, switch the region (top right) to Europe (Stockholm) eu-north-1.
  2. Open EC2, then Launch instance.
  3. Name it, choose an Ubuntu image and the t3.micro instance type (free-tier eligible at the time).
  4. Under Key pair, create a new one named codium. The browser downloads codium.pem. This file is your login. Keep it safe and never commit it.
  5. Under Network settings, create a security group (for example codium-ec2) with these inbound rules: SSH (22) from My IP, and HTTP (80) from anywhere. Do not open 8080.
  6. Choose a larger root disk than the default (the small default disk filled up once Docker images were pulled), then launch.
  7. Copy the public IPv4 address from the instance page. Ours was 13.60.3.224.

Without an Elastic IP the public address changes whenever the instance is stopped and started. Allocate one (EC2, Elastic IPs) before you share the link, and associate it with the instance.

C2. Create the database (RDS)

  1. Open RDS, then Create database, engine PostgreSQL, the smallest burstable class (db.t3.micro or db.t4g.micro).
  2. Set a master username and a password. Store the password somewhere private. Do not paste it into chats or commit it.
  3. Under connectivity, set Public access: No, in the same VPC as the EC2 server.
  4. Create a new security group, for example codium-db. After creation, edit its inbound rules: type PostgreSQL (5432), and as the source choose the security group codium-ec2, not an IP address.
  5. Wait until the status is Available, then copy the endpoint (a long hostname ending in rds.amazonaws.com).

C3. Create the cache (ElastiCache)

  1. Open ElastiCache, create a Valkey (or Redis OSS) cache with the smallest node (a cache.t3 or t4g micro).
  2. Keep encryption in transit on. That is why the URL later starts with rediss://.
  3. Give it a security group such as codium-redis with an inbound rule: Custom TCP 6379, source the codium-ec2 group.
  4. Copy the primary endpoint when it is available.

C4. Prepare the server

Over SSH, install what the server needs: Docker (to run submissions), nginx (the front door) and the Postgres client (to apply the schema).

The script, from the beginning

0. Open with the problem, not the technology

It's a coding-contest platform: you write code in the browser, it runs against hidden tests, you get a verdict, and a leaderboard updates live. The interesting problem is that you're running strangers' code, which is slow and dangerous, while keeping the website fast and not losing anyone's submission.

Why this opening works: it states the constraints (slow, untrusted, must not lose data), so every later decision sounds like a consequence and not a choice from a trend list.

1. The split

I split it into two programs. The API handles requests and never runs user code. A separate worker does the judging. They share nothing except two stores. Postgres is the source of truth. Redis holds the queue, the ranking and live notifications, and everything in Redis can be rebuilt from Postgres.

If they push: "Why separate processes?" Answer: independent scaling and failure isolation. A runaway judge can't take down the API, and judging capacity is sized by Little's law (arrival rate times judge time), not by web traffic.

2. Authentication, briefly

Passwords are bcrypt-hashed. Login returns a signed JWT with the user id and a 24-hour expiry, so any API instance can verify it with the shared secret and I need no session store. On verify I pin the algorithm and require an expiry.

If they push: "Downsides of JWT?" You can't revoke a token before it expires, and a token in localStorage is exposed to XSS. Fixes: short expiry with refresh, httpOnly cookies, or a denylist in Redis.

3. The submit request

When you submit, the API validates the input, inserts a row in Postgres with status pending, pushes only the submission id onto a Redis list, and returns 202 immediately. I write to Postgres first so that if Redis is down the submission is delayed, never lost. The queue holds only the id, so there's a single copy of the code and the worker always reads the current row.

If they push: "What if the API dies between the INSERT and the LPUSH?" The row stays pending and is never queued. I know it. The lightweight fix is a sweeper that re-queues old pending rows. The rigorous fix is a transactional outbox. I haven't built either. Say that plainly, then say which one you would build first and why.

4. The queue and the blocking pop

The worker blocks on BRPOP. A normal pop on an empty list returns at once, so you'd poll with sleeps. With BRPOP Redis parks the connection and wakes the worker the moment a push arrives, so there's no polling and the latency is tiny. Redis is single-threaded for commands, so each element goes to exactly one waiting client. I use a 5-second timeout so the loop can notice a shutdown signal.

If they push: "What if the worker crashes after the pop?" The id is gone from Redis, because a list is at-most-once. Postgres still has the row, stuck in running. A sweeper fixes it. Redis Streams with consumer groups and acknowledgements would give at-least-once delivery properly. Then say why you accepted this: it's a small system, and the data is never lost.

5. The claim

Before judging, the worker claims the job with a conditional update: set running where status is still pending. Postgres makes that atomic, so even if an id were delivered twice, exactly one worker sees one affected row and the other does nothing. I don't try for exactly-once delivery, which doesn't exist across two systems. I make the processing idempotent instead.

6. The sandbox

Each test case runs in a fresh Docker container with no network, one CPU, a hard memory cap with swap disabled, a process limit against fork bombs, all capabilities dropped, a read-only filesystem, a non-root user, and the code mounted read-only. A wall-clock timeout kills it. Output is capped at 1 MB. The verdict follows from the result: compile failed, timed out, non-zero exit, output mismatch, or all tests passed.

Detail that shows you built it: cancelling the context only kills the docker client, not the container, so I name every container and remove it with docker rm -f.

If they push: "Is that secure enough?" Containers share the host kernel, so a kernel exploit is the remaining risk. For hostile production traffic I'd add gVisor or Firecracker and seccomp profiles, and run judge hosts in an isolated subnet. Also be ready to say that wall-clock time includes about 0.3 to 0.5 seconds of Docker start-up (I add a 1.5-second grace) and that memory is limited but not measured.

7. Verdict, then leaderboard

The worker saves the verdict first, so the leaderboard can never undo it. Then it recomputes that user's standing from Postgres: problems solved, and 20 penalty points for each judged wrong try before the first accepted one. It packs that into one number, solved times a million minus penalty, and writes it to a Redis sorted set. I recompute and overwrite instead of incrementing, so a retry can't double-count, and the whole board can be rebuilt from Postgres if Redis is lost.

If they push: "Why a sorted set?" Updates are O(log n), and the top-k read is already ordered, so there's no ORDER BY over all submissions on every page load. The per-problem cells come from Postgres in one = ANY($1) query, so there's no N+1.

8. Live updates

The worker publishes to a Redis channel. Each API instance holds one subscription and its WebSocket hub copies the message to its connected browsers. I used Pub/Sub because the worker doesn't know which API instance holds which socket, and this works unchanged with several API servers. Each client has a bounded buffer, and a slow client is dropped so it can't stall the broadcast. The browser treats the message only as a signal and refetches the board.

If they push: "Pub/Sub loses messages." Yes: it's fire-and-forget. That's acceptable here because the message is only an invalidate signal, and the client refetches the whole board on reconnect. If I needed guaranteed delivery I'd use Redis Streams.

9. Close with deployment and honesty

It runs on AWS: one EC2 instance with nginx, the API, the worker and Docker, and RDS and ElastiCache in private subnets reachable only from the instance's security group, with TLS to Redis. The gaps I know about: it's HTTP only, there's no sweeper for stuck jobs, there's one global leaderboard with no contest timer, and I haven't load-tested scale-out. I'd fix those in that order.

The API and the worker never talk to each other directly. They share only Postgres and Redis. That is what lets them scale and fail independently.

1. Browser (React + Vite app)

  • Job: the editor, the submit button, the verdict, the leaderboard and the live pipeline diagram.
  • Receives: static files from nginx; JSON from the API; WebSocket messages.
  • Sends: POST /api/register, /api/login, /api/submit (with Authorization: Bearer <JWT>), polls GET /api/submissions/{id} every 700 ms, GET /api/leaderboard, opens /ws/leaderboard.
  • How it works: after the 202 it polls status, and a WebSocket push wakes the poll early. If no push arrives within 4 s it shows a red "no live push" state. The Pipeline diagram lights nodes only from events the browser actually saw.
  • Setup: npm run build produces dist/, which is copied to /var/www/codium on EC2. In dev the API is localhost:8080 through an SSH tunnel; in production it is window.location.origin.
  • Connected to: nginx only. It never talks to Postgres or Redis.

2. nginx (front door on EC2)

  • Job: serve the built site and forward API and WebSocket traffic, so the browser sees one origin on port 80 and port 8080 stays closed to the internet.
  • Receives: all public HTTP from the browser.
  • Sends: files from /var/www/codium (with SPA fallback to index.html), or a proxied request to 127.0.0.1:8080.
  • How it works: location blocks for /api/, /ws/ (with the Upgrade headers and a 3600 s read timeout so idle sockets survive) and /healthz.
  • Setup: install nginx on the instance, put the server block from deploy/nginx.conf in place, reload nginx. The security group must allow port 80.
  • Connected to: the browser (in) and the Go API (out).

Honesty note: the exact install steps (conf.d vs sites-enabled) are the standard ones, not confirmed against what you typed. The config file in the repo is the source of truth.

3. Go API (cmd/api, internal/api)

  • Job: authenticate, validate, record, enqueue, answer fast. It never runs user code.
  • Receives: proxied HTTP from nginx: register, login, list problems, submit, get submission, leaderboard, health.
  • Sends: SQL to Postgres; LPUSH to Redis; JSON back; it also hosts the WebSocket hub (component 10).
  • How it works: Go 1.22 ServeMux method+path patterns, auth middleware that puts the user id in the request context, parameterised SQL, MaxBytesReader of 1 MB, code capped at 64 KB. Unique violation maps to 409, foreign-key violation to 404. getSubmission filters by user_id so you can't read someone else's code.
  • Setup: cross-compile and copy up, then run with env vars DATABASE_URL, REDIS_URL, JWT_SECRET, PORT.
  • Connected to: nginx (in), Postgres, Redis (out).

4. Auth (internal/auth, inside the API)

  • Job: turn a password into a token, and a token into a user id.
  • Receives: username and password on login; a bearer token on every protected request.
  • Sends: a signed JWT (HS256, user id in sub, 24 h expiry); the user id into the request context.
  • How it works: bcrypt hashes the password (72-byte limit). Verify pins the algorithm and requires an expiry. Login returns the same error for unknown user and wrong password.
  • Setup: one secret, JWT_SECRET, shared by every API instance. That shared secret is why no session store is needed.
  • Connected to: Postgres (the users table) via the API.

5. PostgreSQL on RDS (source of truth)

  • Job: durable storage for users, problems, tests, submissions and verdicts.
  • Receives: SQL from the API and the worker.
  • Sends: rows back. It sends nothing on its own.
  • How it works: constraints enforce the rules (UNIQUE usernames, CHECK on status and verdict). status (pending, running, done) is separate from verdict. A composite index serves "my submissions for this problem, newest first", and a partial index covers only unfinished rows.
  • Setup: create the RDS instance, private (no public access), attach a security group that allows 5432 only from the EC2 security group, then run migrations/001_init.sql and seed problems. Never paste the master password in chat or git.
  • Connected to: API and worker only.

6. Redis list judge:queue (the job queue)

  • Job: hand submission ids from the API to the workers.
  • Receives: LPUSH of an id from the API.
  • Sends: an id to exactly one worker that is blocked in BRPOP.
  • How it works: push on the left, pop from the right gives FIFO. Redis runs commands on a single thread, so each element goes to one client. A blocked BRPOP is woken by the push, so there is no polling. It is at-most-once: an id popped by a worker that then crashes is gone from Redis (Postgres still has the row).
  • Setup: an ElastiCache (Redis/Valkey) node in the same VPC, security group open on 6379 only to the EC2 security group, and a rediss:// URL because in-transit encryption is on.
  • Connected to: API (producer), worker (consumer).

7. Judge worker (cmd/worker, internal/judge)

  • Job: take an id, run the code against the tests, write the verdict, update the ranking.
  • Receives: an id from BRPOP; the code and tests from Postgres.
  • Sends: the claim and verdict to Postgres; docker run commands; ZADD and PUBLISH to Redis.
  • How it works: WORKERS goroutines each loop on BRPOP with a 5 s timeout, so each can notice shutdown. It claims the job with a conditional UPDATE, so a duplicate delivery does nothing. An infrastructure failure puts the row back to pending instead of inventing a verdict. On SIGTERM it stops taking jobs but finishes the one in flight.
  • Setup: cross-compile ./cmd/worker, run on the same EC2 instance (it needs Docker), same env vars plus WORKERS. The ubuntu user must be allowed to run docker.
  • Connected to: Redis list, Postgres, Docker, Redis ZSET and Pub/Sub.

8. Docker sandbox (internal/judge/sandbox.go)

  • Job: run one untrusted program on one test input, safely.
  • Receives: the source file mounted read-only at /work, and the test input on stdin.
  • Sends: stdout (capped at 1 MB), the exit code, and whether it timed out.
  • How it works: a fresh container per test with no network, 1 CPU, a memory cap with swap equal to memory, a pids limit, all capabilities dropped, read-only root, a tmpfs /tmp, and a non-root user. Containers are named so a timeout can docker rm -f them. Exit 137 means the memory kill and is reported as Runtime Error. Output is compared after trimming trailing whitespace; the loop stops at the first failing test.
  • Setup: install Docker on the instance and pull the language images (gcc:13, golang:1.22-alpine, python:3.12-alpine). Not yet done on your box: the disk filled once, so C++ and Go are unverified.
  • Connected to: the worker only.

9. Redis sorted set + Pub/Sub (leaderboard)

  • Job: hold the ranking, and announce changes.
  • Receives: ZADD with a user's score; PUBLISH from the worker.
  • Sends: top-k via ZREVRANGE to the API; each published message to every subscriber.
  • How it works: score = solved × 1,000,000 − penalty (20 per judged wrong try before the first accepted). It is recomputed from Postgres and overwritten, never incremented, so retries are safe and the board can be rebuilt. Pub/Sub is fire-and-forget; the message is only an invalidate signal.
  • Setup: the same ElastiCache node as the queue; no extra setup.
  • Connected to: worker (writes), API (reads and subscribes).

10. WebSocket hub (internal/ws, inside the API)

  • Job: push "the board changed" to every connected browser.
  • Receives: messages from the Redis subscription (one per API instance); WebSocket connections from browsers via nginx.
  • Sends: the message to every client.
  • How it works: one writePump and one readPump per connection, a 30 s ping and 60 s pong. Each client has a send buffer of 16; if it fills, that client is dropped, so one slow browser can't stall the rest. Origin checking is open (a known gap).
  • Setup: nothing separate. It starts with the API; nginx must forward the Upgrade headers.
  • Connected to: Redis (in), browsers (out).

Why the schema looks like this

  • Constraints do the policing. UNIQUE, CHECK and REFERENCES mean a bug in Go cannot create an impossible row.
  • status and verdict are separate. status is the job lifecycle. verdict is the answer and stays NULL until judged. "Is it finished?" and "was it right?" are different questions.
  • The partial index ignores finished rows, so it stays small no matter how many submissions accumulate.
  • Test cases are their own table with ON DELETE CASCADE so deleting a problem cannot orphan them.
  • Postgres vs Redis: Postgres gives durability and constraints. Redis gives speed. Anything a user would be angry to lose lives in Postgres.

6a. Deep dive: authentication

Passwords: bcrypt

Passwords are hashed with bcrypt: salted and deliberately slow, so a stolen database is expensive to brute-force. The salt and cost are stored inside the hash string. I reject passwords over 72 bytes because bcrypt would silently ignore the rest.

Register: validation, injection safety, and the signup race

  • SQL injection: parameter placeholders keep data separate from the query text.
  • Race on usernames: a SELECT then INSERT lets two simultaneous requests both pass the check. The UNIQUE constraint makes Postgres pick exactly one winner, and error 23505 becomes HTTP 409.
  • Body cap: MaxBytesReader bounds memory per request.

Login: no username enumeration

JWT: stateless, algorithm pinned, expiry required

The token carries the user id in sub and is signed with HMAC-SHA256. Any API instance that holds the secret can verify it, so there is no session store and the API scales horizontally. On verify I pin the algorithm and require an expiry, which blocks alg: none and algorithm-swap attacks.

A stateless token cannot be revoked before it expires, and a token in localStorage is readable by any script on the page (XSS). Fixes: short-lived access tokens with refresh tokens, httpOnly cookies, or a denylist in Redis.

Middleware: verify once, pass the id by context

Handlers read the user with auth.UserID(ctx) and never parse tokens. The context key is an unexported struct type, so no other package can collide with it.

6b. Deep dive: POST /api/submit

Every choice, explained

  • 202, not 200. The request was accepted for processing; the result is not ready.
  • DB before queue. If Redis fails after the insert, the row is still pending and can be re-queued. The reverse order could queue an id for a row that does not exist. The failure mode is "delayed", never "lost".
  • Only the id in the queue. The queue stays tiny, there is one copy of the code, and the worker always reads the current row.
  • Foreign-key error becomes 404, not a 500, so a bad problem id is a client error.
  • 64 KB code cap and 1 MB body cap bound memory and DB growth.

This is a dual write: Postgres and then Redis, with no shared transaction. If the API dies between the two, the row sits as pending and is never queued. The rigorous fix is a transactional outbox: write the job to an outbox table in the same transaction and let a relay push it. My lightweight version would be a sweeper that re-queues old pending rows. I have not built it.

6c. Deep dive: the judge worker

Process shape and graceful shutdown

N goroutines each block on the queue, so N submissions are judged at once. On SIGTERM the context is cancelled, the loops stop taking jobs, and wg.Wait() lets running jobs finish.

The loop: blocking pop, no polling

The atomic claim

A conditional UPDATE is atomic in Postgres. If the same id were delivered twice, exactly one worker sees one affected row and the other does nothing. Delivery can be duplicated; processing cannot.

The compile step is looser on purpose: /work is read-write so the compiler can write the binary. The run step is the strict one.

Timeouts: kill the container, not just the CLI

Cancelling the context kills the docker client process, but the container keeps running. I give every container a unique name and remove it by name. Without that, an infinite loop would leak a container forever.

Output cap

Containers share the host kernel, so a kernel exploit is still possible. For hostile production traffic I would add gVisor or Firecracker, seccomp profiles and disk quotas. Wall-clock time includes Docker start-up (about 0.3 to 0.5 s), so I add a 1.5 s grace; a real judge measures CPU time with cgroups. memory_mb is limited but never measured, so it is NULL.

6e. Deep dive: the leaderboard

Rule (ICPC style). More problems solved wins. Ties break on lower penalty. Each judged wrong try before the first Accepted on a solved problem adds 20.

Packing two sort keys into one number lets a single sorted set order users correctly. One extra solve is worth 1,000,000, which no realistic penalty can reach.

Recompute, do not increment

After each verdict I recompute that user's standing from Postgres and ZADD it. ZADD with an existing member just overwrites the score, so running it twice is harmless. ZINCRBY would double-count on a retry. And if Redis is wiped, the whole board can be rebuilt from Postgres.

Reading the board

Ranking comes from Redis; the per-problem cells (solved, tries) come from Postgres in a single query, which avoids an N+1 pattern. Each store does what it is good at. ZADD is O(log n) and the top-k read is O(log n + k), against a scan of all submissions for an ORDER BY.

6f. Deep dive: WebSocket hub and Pub/Sub

Why Pub/Sub

With two API servers behind a load balancer, a browser is connected to only one. The worker is a different process and knows no sockets. So the worker publishes once to Redis, every API instance subscribes, and each pushes to its own browsers.

flowchart LR
  W[Worker] -->|PUBLISH| R[(Redis Pub/Sub)]
  R --> A1[API instance 1]
  R --> A2[API instance 2]
  A1 --> B1[Browsers on 1]
  A2 --> B2[Browsers on 2]

A slow client must not stall everyone

Each client has a bounded channel. select with default makes the send non-blocking. The mutex protects the client map.

One reader and one writer per connection

Ping and pong detect half-dead connections, such as a laptop that went to sleep, which TCP alone would not notice for a long time.

Redis Pub/Sub is fire-and-forget: a message sent while a subscriber is disconnected is gone. That is acceptable here because the message is only an invalidate signal. On reconnect or the next page load the browser refetches the full board. CheckOrigin returns true because the board is public read-only data; for private streams I would check the Origin header.

6g. Deep dive: the frontend and the live diagram

One API layer

In development it talks to localhost:8080 through an SSH tunnel. In a production build it uses the page's own origin, because nginx serves the site and proxies the API. One origin means no CORS problem.

Submit, then poll, woken early by the push

The browser also opens the leaderboard socket and waits for a message about its own username. When it arrives, the poll loop wakes early. Polling alone is a correct fallback; the socket is an optimisation.

  1. Workers first. Judging is the only expensive step. Run more worker processes, raise WORKERS, or put workers on their own hosts. They share only the queue and the database, so this needs no code change. Size by Little's law (chapter 2).
  2. API instances. The API is stateless because of JWT, so put several behind a load balancer. WebSockets already fan out correctly through Pub/Sub.
  3. Database. Add a read replica for leaderboard cells and problem reads. Add connection pooling (RDS Proxy or pgbouncer) when instance count grows.
  4. Queue. If volume or delivery guarantees demand it, move to Redis Streams with consumer groups, or SQS.
  5. Isolation. Run judge hosts in a separate, locked-down subnet so a sandbox escape cannot reach the API or database hosts.

I have run one API and one worker. The design allows scale-out; I have not load-tested it.

12. Interview questions with answers

Why a queue? Why not judge inside the request?

Judging takes seconds and is CPU heavy. Inside the request it holds connections, times out under load, and ties API capacity to judge capacity. A queue absorbs bursts, workers drain at their own pace, and each side scales alone.

What if two workers pop the same job?

The claim is UPDATE ... SET status='running' WHERE id=$1 AND status='pending'. Postgres makes it atomic, so only one worker gets one affected row.

What if Redis dies?

Every submission is already in Postgres as pending, so nothing is permanently lost; judging is delayed. After Redis returns I re-queue pending rows and rebuild the leaderboard from Postgres. That is why Postgres is the source of truth.

What if the worker crashes mid-judging?

The row stays running and the user waits. I have not built the sweeper. The design is to requeue running rows older than a timeout. That is safe because the claim, the verdict write and the leaderboard recompute are all idempotent.

What if the API crashes between the INSERT and the LPUSH?

The row is pending but not queued. The same sweeper fixes it. I order DB first so the failure is "delayed", never "queued with no row". A transactional outbox is the fully correct solution.

How do you stop malicious code?

Defence in depth: no network, CPU, memory and pid limits, no swap, read-only root with a small tmpfs, all capabilities dropped, no-new-privileges, non-root user, read-only code mount, a wall-clock timeout that removes the container by name, and an output cap. The remaining gap is the shared kernel, so for hostile traffic I would add gVisor or Firecracker.

Why Pub/Sub for WebSockets?

The worker does not know which API instance holds which socket. Publishing once to Redis lets every API instance receive it and push to its own clients, and the worker and API need no direct link.

Pub/Sub is fire-and-forget. What if a client misses a message?

The message is only an invalidate signal. On reconnect or the next load the client refetches the whole board. If I needed guaranteed delivery I would use Redis Streams.

Why recompute the leaderboard instead of ZINCRBY?

ZINCRBY is not idempotent: a retry double-counts. Recompute plus ZADD overwrites with the correct value, so it is safe to repeat and it self-heals.

Why a sorted set instead of ORDER BY?

O(log n) updates and O(log n + k) top-k reads, already sorted, with no scan of all submissions on every page load. Postgres still holds the truth and can rebuild it.

How would you scale it?

Workers first, since judging is the cost: add processes or hosts. Then API instances behind a load balancer (stateless thanks to JWT, WebSockets fan out via Pub/Sub). Then a read replica and connection pooling for Postgres. If delivery guarantees matter, move the queue to Streams or SQS.

JWT: why, and what are the downsides?

Stateless: any instance verifies with the secret. Downsides: no revocation before expiry and exposure to XSS when stored in localStorage. Mitigate with short expiry and refresh tokens, httpOnly cookies, or a denylist.

How is a signup race handled?

By the UNIQUE constraint, not check-then-insert. The database serialises it, and I map error 23505 to HTTP 409.

Why 202?

The request was accepted for processing and the result is not ready. 200 would imply completion.

Why does the worker use context.Background() for a job?

So a shutdown signal cannot abort a half-judged job. The loop stops taking new jobs; running ones finish, and wg.Wait() blocks until they do.

Is the live diagram real?

Yes. Each stage is triggered by something the browser observed: the 202, the polled status becoming running and done, and the WebSocket push for my username. If the push never arrives it shows red instead of faking success.

What would you do next?

HTTPS and a domain, an Elastic IP, a stuck-job sweeper, Redis Streams or an outbox, real CPU and memory measurement, contest timers, rate limiting, metrics with Prometheus and Grafana, CI/CD, and secrets in AWS Secrets Manager.
